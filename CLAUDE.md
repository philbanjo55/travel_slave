## Data safety (hard rules)

- **Never DELETE rows from `stops`.** Deleting a stop cascades (`ON DELETE CASCADE`) to:
  `stop_photos` (Phil's photos), `weather_forecasts` (forecast archive), `stop_sun_pairs` (vantage links), `model_grid_points`, `drive_times`. `exposures.stop_id` is set NULL.
- **Move stops with `UPDATE stops SET day_id, position`**, never insert-plus-delete. Inserting a new stop is allowed.
- **"Remove a stop" = set it aside:** `day_id = null` (the apps only show stops on a day) and `solver_stop_settings.tier = null` (the planner skips it), notes kept; `trip_readiness` lists them as "set aside". Do the same on the trip's training copy. Saved-for-later ideas are stored the same way with names starting "Idea: " (Grand Teton: 8 NPS ski/snowshoe routes, 23 Oct).
- **Stop names are the place only** (Phil, 26 Oct 2026): no time, light or shot in the title ("Oxbow Bend", not "Oxbow Bend — Sunrise"); the planner picks the time. Place qualifiers ("South Jenny Lake — East Shore") and logistics names stay.
- The repo is public and ships the anon/publishable key, and the app (branch `update`) writes `stops`, `days`, `trips`, `stop_photos`, `exposures` and the `photos` storage bucket with that key. Do NOT tighten RLS on those without moving the app's writes behind an edge function first (an Oct 2026 lock broke the app for 25 min; the `anon_no_*` policies are now neutralised to `true`).
- Before judging what the app does, read the code on branch `update`, not `master`.
- **Security advisor (25 Oct 2026, `20261026030000_security_advisor_fixes`):** trip views run as the caller (`security_invoker`); backend-only SECURITY DEFINER functions are closed to anon/authenticated. Still flagged on purpose: the sun-planner RPCs and `claude_spend_summary` (the app calls them with the public key), 77 "RLS, no policy" tables (locked = fine), `pg_net` in public (Supabase-managed), small inlined SQL helpers without `search_path`, and Phil's other-project views `cv`, `calendar_*`, `v_print_*` (readable with the public key; Phil, 25 Oct 2026: "keep as is", do not change).

## Database conventions

- pg_cron runs in GMT/UTC. Faroe time is UTC+1 in summer, UTC+0 from late Oct to late Mar.
- `cron.job` calls edge functions with `net.http_post`; pg_net times out at 5 s but the function keeps running. Don't rely on the HTTP response.
- New tables get RLS enabled automatically (`ensure_rls` event trigger). With no policy the app/web viewers read zero rows — add a SELECT policy if the client needs it.
- `prune_weather_forecasts()` (weekly) strips `raw` blobs older than 21 days. `weather_forecasts` is a display table, not an archive.
- **Disk IO budget (Supabase emailed 21 Oct 2026):** the compute has a daily IO burst budget, and temp files count (work_mem is 3.5 MB on Micro, so big sorts/aggregates spill). Big one-off computes (DEM loads, terrain recomputes, shot setup for a new trip) each write GBs of temp: spread them over days. Never call a function per row when it can read `weather_forecasts.raw` (the solver-plan cron did, via `solver_trip_tz`, and timed out on 20 Oct); look up per-trip values once.
- The Supabase MCP connector hangs (times out, nothing runs) on SQL whose text contains the word "drop" or a `delete from` (even inside a string or `on commit drop`): reword it, or build the keyword in `execute` (`'del' || 'ete from ...'`) for tests. It also asks a confirmation question (which never reaches Phil, so the call times out and must not be retried that turn) for an UPDATE without a WHERE clause: always add one (`where trip_id is not null`). Long note text can trip it too (24 Oct: a grooming note hung it three times): send it as `convert_from(decode('<base64>','base64'),'UTF8')`. A semicolon inside a string literal in an UPDATE also makes it ask (28 Oct: every planner_versions update whose note held a `;` stalled; the same update without it went through): keep `;` out of string literals or send the text as base64.
