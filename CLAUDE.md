# travel_slave — notes for Claude sessions

Philm+Frame trip planner: Expo/React Native app (`src/`), static web viewers (`faroes-web/`, `iceland-web/`), and a Supabase backend (project `ohshrzlvvxyovcjmdajc`). Most backend logic lives in the database and edge functions, not in this repo — read the live definitions before changing anything.

## Data safety (hard rules)

- **Never DELETE rows from `stops`.** Deleting a stop cascades (`ON DELETE CASCADE`) to:
  `stop_photos` (Phil's photos), `weather_forecasts` (forecast archive), `stop_sun_pairs` (vantage links), `model_grid_points`, `drive_times`. `exposures.stop_id` is set NULL.
- **Move stops with `UPDATE stops SET day_id, position`**, never insert-plus-delete. Inserting a new stop is allowed.
- The repo is public and ships the anon/publishable key, and the app (branch `update`) writes `stops`, `days`, `trips`, `stop_photos`, `exposures` and the `photos` storage bucket with that key. Do NOT tighten RLS on those without moving the app's writes behind an edge function first (an Oct 2026 lock broke the app for 25 min; the `anon_no_*` policies are now neutralised to `true`).
- Before judging what the app does, read the code on branch `update`, not `master`.
- `reset_test_bed()` deletes and rebuilds trip `7e57bed0-0000-4000-8000-000000000001` only. Use that trip for experiments.

## Branches and releases

- **`update`**: the app plus everything else. Pushing app files runs `.eas/workflows/update.yml`: fingerprint the native side; if an APK with that fingerprint exists, publish an instant (OTA) update to channel `preview`; otherwise build a new APK. `runtimeVersion` uses the fingerprint policy, so an update only reaches an APK it matches. Backend/docs/web commits trigger nothing. All EAS jobs use the `preview` environment (the `preview` build profile's default) so fingerprints line up.
- **Test builds:** eas.json profile `test` (`APP_VARIANT=test`) builds "Philm+Frame TEST", package `com.philmframe.app.test`, channel `test`, which installs side by side with the real app. `.eas/workflows/test-build.yml` runs on pushes to the work branch only, like update.yml: instant update to channel `test` when a TEST APK with the same fingerprint exists, else a new TEST APK.
- **TEST-only features:** `src/utils/variant.ts` `IS_TEST_APP` (from the built config name/package, no app.config change). The solver Planner (sparkles icon on the trip page -> `PlannerScreen`, `PlanScreen`; got/nailed tick and nearest webcams on the stop screen, `components/planner/`) shows only there. Its writes go through edge function `solver-actions` (mark_shot, frames with signed URLs, label_frame, plan, apply_preview, apply = test-bed trip only); plans/settings are read directly (`app_read` select policies on solver_runs, solver_plans, solver_stop_settings).
- **App stack (SDK 58 since 20 Oct 2026, tested by Phil on the TEST build first):** Expo SDK 58, RN 0.88, React 19.3, New Architecture on (mandatory since RN 0.82), Reanimated 4 + react-native-worklets (babel-preset-expo adds the worklets plugin itself; don't list it in `babel.config.js`), file-system calls via `expo-file-system/legacy`, `babel-preset-expo` as a direct devDependency, React Navigation 7 (v6 stack calls `InteractionManager`, which RN 0.88 removed: crash on launch; v7 `navigate` no longer pops back to a screen already in the stack, use `popTo`). Native upgrades go through the TEST build first, then merge into `update`, which builds a new real APK (new fingerprint).
- **`main`**: old "build an APK" branch (`.eas/workflows/build.yml`). No longer needed for releases; kept as a manual fallback.
- **`master`**: GitHub default branch. Netlify deploys the web viewers (`faroes-web/`, `iceland-web/`) from it, and GitHub only runs scheduled workflows (`webcam-clip`) from the default branch.

## Edge functions

- The repo copy of each function must match what is deployed. Before editing one, fetch the deployed source (`get_edge_function`) and diff — the repo has drifted before (weather-pull v33 vs deployed v35).
- `weather-pull` (v35, `index.ts` + `logic.ts`): per-day display forecasts into `weather_forecasts`. Triggered by pg_cron jobs `hourly-weather-pull` and `daily-preview-refresh`.
- `weather-ensemble-pull`: nightly ensemble archive into `weather_ensemble` (per 0.25° cell, member arrays; `*_c10`/`*_kmh10`/`*_mm10` are value × 10). pg_cron `17 22 * * *` UTC. Separate from weather-pull on purpose. Never schedule Open-Meteo pulls at :07 — hourly-weather-pull runs then and the shared per-minute quota returns 429s. **Outlook:** when a live trip has days 4–15 days out, ECMWF (only) is pulled 16 days and kept to the last such trip day (6-hourly beyond 144 h; `solver_build_scores` joins those slots to the nearest 6-h step). `{outlook_until}` in the body forces a window for tests. Nightly plans: one per build day, multi-day over the first 3 days only (CPU).
- `webcam-archive`: hourly (`37 * * * *`, night frames with sun < -6 deg skipped) saves each active `webcam_cameras` row (any trip; per-camera `image_url`, `region`, `source`, `permission_note` — always get permission before adding a camera) to Storage bucket `webcams`, haze metrics into `webcam_frames`. Full images kept 7 days, the frame nearest each camera's solar noon kept forever (v14; was 12 UTC, night outside Europe). Labels from Claude (`claude-opus-5-5`, effort low, structured output, `fallbacks: "default"`; secret `ANTHROPIC_API_KEY`, `CLAUDE_LABELS=false` off switch, `CLAUDE_DAILY_CAP` default 400): label, hills_visible, cloud_on_hills, sun_on_land, note. Phil's taps go to `phil_label` (never over Claude's). `{backfill: n}` labels stored daylight frames without a label. Gemini code removed. **Stale frames:** cameras can freeze and keep serving an old picture (F-41 served its 16:25 image at 18:00 UTC), so each frame stores `image_sha256`, `fetched_at` and Claude's reading of the printed time (`camera_time_text`, camera-local; `webcam_cameras.tz`); trigger `webcam_frame_stale` sets `stale` (`repeat image` within 12 h, or `camera clock HH:MM` when the printed time is over 45 min from fetched_at). Repeats skip the Claude call. Stale frames are excluded from camera tiles, `solver_verify_run` and `solver_backtest_run`.
- **Cameras belong to places, not trips:** any trip with stops within 50 km sees a camera (`solver-actions` `MAX_CAMERA_KM`; the backtest uses 12 km). Faroes: Landsverk F-xx. Grand Teton (Phil got permission by phone, Oct 2026): `GT-MOOSE` (NPS / Grand Teton National Park Foundation livestream at the Moose visitor center, still from the YouTube live thumbnail `i.ytimg.com/vi/XhBUrjhJm1A/maxresdefault_live.jpg`) and `GT-TETONIA` (TetonCam, Tetonia ID, from its Google Cloud archive). Still to find image links for: Jackson Hole Mountain Resort, Grand Targhee, Teton Science Schools (Kelly), WYDOT (permission given; their pages load cameras with JavaScript and the old NWS list links are dead). `image_url` may be a template (`{YYYY}{MM}{DD}{HHmm}`, camera tz, 15-min steps, the file time becomes camera_time_text); every fetch times out after 20 s.
- **Claude spend:** every Claude API call logs tokens and cost to `claude_usage`; `webcam-archive` stops labelling once `claude_spend_month()` reaches `CLAUDE_MONTHLY_CAP_USD` (default 40; Phil's budget is under $50/month for all Claude use). The TEST app shows the month's spend (Planner, Weather Updated alert) via `claude_spend_summary()` (security definer, totals only). F-23 is inactive (road only, no sky; Phil, 20 Oct 2026). `solver-actions` `frames` returns daylight, non-stale frames only (`{trip_id}`: cameras within 50 km of any of the trip's stops, the Planner strip; `{lat, lng, n}`: nearest to a stop; each frame has `taken_at` = camera time, else fetch time, since `captured_at` is only the hour slot; `camera.live_url` fills templated URLs for the Live button, `live_time` its camera-local time; the TEST app reloads Live every 30 s while open); `{camera, at}` returns one camera's stored frame at a time as a signed URL (how to show Phil a frame: this container can't reach Supabase storage or lv.fo).
- `webcam-labels`: token-gated door (`WEBCAM_LABELLER_TOKEN`) for the CLIP labeller in GitHub Actions (`tools/webcam_clip`, `.github/workflows/webcam-clip.yml`, nightly 03:23 UTC). The repo is public: the workflow must never hold the service-role key.
- `webcam-probe`: retired stub (returns 410); delete it from the dashboard.
- `dem-region-load` (POST `{region, south, north, west, east, step=0.0015, zoom=11, row_from, rows=60}`): elevation grid for terrain horizons outside the Faroes, from public AWS terrarium tiles into `dem_regions` / `dem_region_rows` (one band of rows per call, loop on `next_row`; the last call stamps `loaded_at`). Then `dem_region_recompute(region)`. `terrain_profile_compute` uses the Faroe DEM first, else a region grid. Region-grid profiles ignore terrain closer than two grid steps (`terrain_profiles.min_dist_m`; the coarse grid otherwise puts walls beside summits). Loaded: `grand_teton` (634×954, ~1.3 MB).
- `calculate-drive-times`: writes `stops.drive_override_minutes` (previous-stop leg) via Google Directions.
- `solver-drive-matrix` (POST `{trip_id}`): fills `solver_drive_legs` (per spot pair, coords rounded to 3 dp by `solver_trip_spots()`, shared across trips) via the Google Routes matrix API. Incremental: only pairs not yet stored are fetched, so re-running is free unless a stop moved. `solver_drive_matrix` (view) gives stop-to-stop minutes per trip; legs Google can't route (car ferries) go through `solver_ferry_links`. Call it from SQL with `net.http_post` (this container can't reach supabase.co directly).

## Database conventions

- pg_cron runs in GMT/UTC. Faroe time is UTC+1 in summer, UTC+0 from late Oct to late Mar.
- `cron.job` calls edge functions with `net.http_post`; pg_net times out at 5 s but the function keeps running. Don't rely on the HTTP response.
- New tables get RLS enabled automatically (`ensure_rls` event trigger). With no policy the app/web viewers read zero rows — add a SELECT policy if the client needs it.
- `prune_weather_forecasts()` (weekly) strips `raw` blobs older than 21 days. `weather_forecasts` is a display table, not an archive.
- Free plan: database must stay under 500 MB or it goes read-only. Check `pg_database_size` before adding anything that grows nightly. `db_size_check()` logs the size daily to `app_logs`.

## Solver

Spec: `SOLVER_SPEC.md` (in Phil's uploads). Review and corrected build order: `docs/solver/SPEC_REVIEW.md`. Per-stop inputs (backend only, the app never reads them): `solver_stop_settings` (tier, starred shot, light wanted front/side/back/soft, fog_wanted, time_locked; `source` = suggested/phil), resolved by the `solver_stop_inputs` view. Fog/rain/wind are global penalties; waterfalls get a rained-yesterday bonus. `solver_build_scores(trip)` (pg_cron `41 22 * * *`, ~100 s) scores every rated stop's starred shot per 15-min slot per ECMWF member into `solver_scores` (smallint[] x250, tier not baked in); `solver_score_summary` gives mean / CVaR of the worst 11 / P(good). Light geometry is cached in `solver_light_cache`. The nightly job is `solver_nightly(trip)`: build, then `solver_prune_builds` keeps the newest 3 (approved by Phil). `solver-plan` edge function (POST `{trip_id, date?, hotel_stop_id?}`, pg_cron `55 22 * * *` once per build day): beam search over one day from the hotel and back, mean + 0.5 x CVaR, same-subject repeats count only the improvement, top 5 distinct plans + safest into `solver_runs` / `solver_plans`. `trip_date` plans a forecast day as a given trip day (its hotel and its time-locked stops as fixed visits); `multi: true` plans all build days together (a subject counts once, at its best day per member). Nightly: one call per build day plus one multi-day call (dates in the trip's timezone, `solver_trip_tz`). Watch the 2 s edge CPU limit (it was hit once by per-row Intl formatters).
- **solver-plan v0.3 extras:** `trip_date` alone plans that trip day; past the forecast it uses **light-only** scores (`solver_light_terms` from `solver_light_cache`, expanded in the function to 51 made-up sun scenarios s=(k/50)^2, no rain/wind/fog; `solver_light_scores` is the same in SQL). `solver_nightly` tops up the light cache for every trip day (~0.05 s per shot-day). Days start at the previous night's accommodation and end at that night's (move days). Day rules (Phil, 21 Oct 2026): free stops 05:00–23:30 local (`earliest`/`latest`); GOD/S stops may start from 03:45 (`earliest_sunrise`) on forecast days when p_good >= 0.5 there, never on light-only days; multi-day plans keep >= 6 h between back at the hotel and leaving again (relaxed only when bookings force it, listed in `stats.window.rest_relaxed`). Drive: legs under 60 min are free (tie-break only); minutes beyond 60 on one leg cost 1 point/hour (`long_leg_minutes` on each plan). Multi-day beam defaults to 300. Rank 0 = **"my day"**: the trip day's own stops at their time_labels, each with value, p_good, light and best time that day. Visits carry `value`, `p_good`, `peak_at`, `light`, `trip_date`.
- **Shot status** (`solver_stop_settings.shot_status` got/nailed, `shot_value`; set with `solver_mark_shot(stop, status, at?, value?)`): nailed subjects drop out, got ones count only the improvement over shot_value. Phil marks them in chat until the TEST app has the tick.
- **Scoreboard** (`solver_verify`, pg_cron `solver-verify` 23:29 UTC): every passed ECMWF step vs what happened at EKVG (`station_obs_hourly`: mostly_clear, low_cloud, rain, fog) and at the webcams (hills_hidden from top-half edges vs each camera's clear level, or Phil's `hills_visible` label with `label_model='phil'`). `solver_verify_report(days)` gives Brier, skill vs base rate and reliability bins per event and lead. Thresholds are first guesses.
- **Calibration from history** (read-only, not used by the builder until the backtest shows it helps): `metar_history` (EKVG METAR, May 2010-2026, Iowa Mesonet; May 2010 has no cloud groups and drops out via `metar_history_events`), `hist_forecast` (ECMWF IFS deterministic at the EKVG cell from Open-Meteo previous-runs, May 2024-2026; low/mid cloud only at lead 0, total cloud/RH/rain to lead 5), `solver_calibration` (per event x forecast bin x lead: observed frequency vs the member rule; `solver_fit_calibration()`), `may_climatology` (base rates by UTC hour). Load with `calib_queue_history()` then `calib_load_history()`; IEM throttles parallel requests, re-queue failed years one at a time. First result: ECMWF under-forecasts low cloud at Vagar (cloud_low <10% still has a ceiling below 2000 ft 15% of daylight hours, 50-70% has it 65%), and max(low, mid) 10-50% is mostly clear only 23-34% of the time.
- **Backtest** (`solver_backtest`, pg_cron `solver-backtest` 23:33 UTC): every saved plan for a real forecast date, once the date has passed, scored at each visit's peak time against the nearest truth within 12 km (Phil's webcam tap, then Claude's label, then EKVG METAR): hidden -> 0, clear without sun when direct light is wanted -> 0.4, else 1 (fog-wanted stops reversed); baseline = the same source at every daylight hour that day; lift = realized - baseline. Visits without truth are retried for 3 days. Read `solver_backtest_summary(days, tiers, min_lead)` (latest run per date and lead; `solver_backtest_report` v1 counts dev runs too). `solver_backtest_run(true)` is a dry run on today's plans that rolls back and reports the summary.
- **Truth is per place:** the scoreboard uses every METAR station within 30 km of a live trip's stops (EKVG, KJAC); the backtest takes any `metar_stations` row within 12 km, with daylight from `sun_position` at the airport.
- **Calibration for other places/months:** `calib_queue_month(site, month, years[], forecast_years[])`, then `calib_load_history()` (matches US IDs without the K: IEM returns `JAC`), then `solver_fit_calibration_months(site, source, months[])`; base rates in `metar_climatology`. KJAC Dec/Jan loaded (METAR 2016-2026, ECMWF 2024-2026): model RH misses valley inversion fog (fog ~8-9% at 08-09 MST, RH almost never >= 85%).
- **New trip: follow `docs/NEW_TRIP_SOP.md`**; phase 1 (trip, days, stops, hotels) is one call, `trip_import(json, dry_run)` (checks first, insert only, adds hotel logistics stops) (every step, what Phil provides, known gaps) and check with `select * from trip_readiness('<trip>')` (ok/todo/wait/warn/info per item). In short, for the solver (done for Grand Teton Winter 2026, `20261021250000_teton_solver_setup`): shots (`scout_subjects` + `scout_vantages` + `stop_sun_pairs`; stand spot = stop coords if unknown), a region DEM if outside the Faroes, suggested `solver_stop_settings` (source `suggested` until Phil confirms), `solver-drive-matrix` for the trip, cameras with permission near the stops, a METAR station within 30 km. The nightly jobs pick the trip up once it has settings.
- `solver_trip_tz` validates the name with `at time zone` instead of scanning `pg_timezone_names` (0.5 s per call); still materialize it once per trip in big queries.
- **Apply:** `solver_apply_plan(run, rank)` previews, `(run, rank, true)` applies (UPDATE stops day_id/position/time_label/drive_override_minutes only, logged in `solver_applies`), `solver_undo_apply(id)` reverts. Plan stops go to their plan day at the plan time; others stay; the day's first and last stops stay at the ends. Only apply to Phil's real trip when Phil asks.

Plans are reviewed in chat for now. Planner UI (an icon top right of the trip page opening a Planner screen; mockups in Phil's artifacts) goes in the TEST app only; the real app gets none of it until Phil signs off the solver as finished and tested. No web page. The solver writes proposals to its own tables and never writes to `stops` except through an explicit apply step.
